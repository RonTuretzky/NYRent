# RENT trading market

The v4 build adds a collateralized ERC-20 RENT market alongside the existing fixed-price
ERC-1155 contracts. It uses Uniswap's PoolManager; buying and selling RENT are actual AMM
swaps. Existing fixed-price deployments and operator tools remain intact.

Deployment is explicit: `web/src/chain/v4-deployments.json` lists verified live markets.
An empty entry means no v4 market is configured on that chain. Tests, local manifests and
fork addresses are not production deployment evidence. The website falls back to the
existing fixed-price market and labels examples when no matching market is available.

## Contract boundaries

- `RentV4Factory` fixes the collateral, oracle and canonical PoolManager. Anyone can create
  a market with immutable terms. The factory creates the RENT token and registers its exact
  PoolKey before initializing the pool. Its CREATE2 hook address encodes the callbacks.
- `RentV4Market` is the RENT ERC-20 and its isolated escrow. `depositAndMint` pulls one
  collateral base unit for every RENT base unit minted. It rejects transfer-fee tokens.
  Only this contract can mint/burn; the noncustodial hook never owns the backing collateral.
  Token decimals match collateral (6 or 18). No yield strategy is enabled.
- `RentV4Hook` authenticates PoolManager callbacks and exact PoolKeys. Swaps and additions
  close at `saleEnd`; liquidity removal and direct token transfers freeze during observation.
  Settlement or expiry releases the removal lock. Swaps never reopen after the cutoff.
- `RentV4Router` settles the singleton's debts from the caller and sends credits directly to
  the specified recipient. Swaps have deadlines, bounded input and minimum output. Liquidity
  positions belong to the caller and their tick range; another caller cannot withdraw them.
  Callback authorization is bound to the initiating request and consumed before token calls.
- `CredailyRentOracle` is unchanged. The new market reads its existing authenticated
  observations and binds its base value to an observation when constructed.

The factory is generic and permissionless. The app deliberately selects one explicit market:
September 2026 baseline, September 2027 observation window, 3%–8% coverage band. It checks
the baseline month and strikes before presenting that market as live. Creating another market
does not make it appear automatically in the default UI.

## Backing, liquidity and residual ownership

An insurer depositing C receives C RENT and C nontransferable residual shares. Selling RENT
does not transfer those residual shares. All RENT is a potential claim: insurer inventory and
tokens held in liquidity positions count too. Total supply must not be labeled “sold.”

AMM liquidity is separate from escrow. Depositing C as backing does **not** provide the extra
collateral needed for a two-sided LP position. Removing liquidity returns the current token
mix and accrued fees; it does not release backing from escrow.

After settlement each holder may burn RENT for `amount × payoutRatio / 1e18`, rounded down.
Insurers must also redeem any RENT they still own, including tokens recovered from LP
positions. After `redeemEnd`, an insurer may withdraw:

```
(totalDeposited - paidOut) × insurerResidualShares / totalDeposited
```

The numerator/denominator are fixed after the claim deadline, and withdrawals are one-shot.
Unclaimed payouts are shared across original depositors, rather than tracked to the issuer
of each fungible token. Donations and division dust remain in escrow. There is no privileged
sweep. Before withdrawals, escrow covers the outstanding payout liability. After withdrawals,
expired RENT has no redemption right even if it remains in circulation.

## Lifecycle

| Phase | Mint / swap / add LP | Direct RENT transfer | Remove LP / collect fees | Redeem |
|---|---|---|---|---|
| Before saleEnd | Yes | Yes | Yes | No |
| saleEnd to obsStart, if distinct | No | Yes | Yes | No |
| Observation, before settlement | No | No | No | No |
| Settled, through redeemEnd | No | Yes | Yes | Yes |
| After redeemEnd, including no email | No | Yes | Yes | No |

The configured market sets saleEnd equal to obsStart. Settlement accepts a signed timestamp
within `[obsStart, obsEnd]`; the first successful qualifying **settlement transaction** wins.
It does not prove that an email was chronologically earliest or that every earlier email was
submitted. A later settlement cannot reopen expired redemption rights.

The token lock prevents direct ERC-20 transfers while the canonical hook blocks canonical
swaps/LP withdrawals. It cannot freeze custodial IOUs, third-party LP ownership, or already
internalized accounting such as ERC-6909 claims in unrelated pools. No global prohibition on
economic exposure trading is claimed. Third-party routers must choose to support this hook.

## Prices and fees

The initializer chooses the first spot price; subsequent swaps change it through Uniswap's
concentrated-liquidity math. Quotes come from the actual v4 Quoter, and histories from the
matching PoolManager Swap events. Thin liquidity may make a target amount impossible or
expensive; spot price alone is not an executable quote.

The immutable fee increases linearly from 0.30% at creation to 1.00% at the trading cutoff.
Fees accrue to LPs. There is no owner-set fee, volatility feed or inventory oracle in the hook.
The first UI supports full-range positions; the router also accepts valid concentrated ranges.
The existing fixed-price agent remains available with Bankr execution held; automatic v4
range quoting is a separate operator integration, not a background action enabled by this UI.

For display, `3% + 5% × price` is a **price-equivalent growth level**, not E[g]. Clipping the
payout means different outcome distributions can give the same price. Risk, time discounting,
fees and liquidity also affect price. The renter calculator covers the 3%–8% band only and
follows a Manhattan office index, not an individual residential lease.

The insurer calculator's 4% yield is explicitly a scenario for a planned feature. The current
escrow earns no strategy yield. With its defaults, modeled premium is 2,850, hypothetical
yield is 4,000 and worst-case net is -3,150. Without yield, worst-case net is -7,150. The
6.425% insurer break-even versus 4.425% renter break-even comes from modeled yield per sold
claim, not a hidden “loading” term.

## Large authentic emails

Arbitrum's sequencer admission limit can reject the 104,068-byte direct fixture transaction,
even when `eth_estimateGas` succeeds. `ChunkedObservationSubmitter` stores immutable
STOP-prefixed body chunks in separate transactions and appends an inline tail at submission.
It reconstructs the exact body, checks SHA-256 against the preflight email ID, and calls the
unchanged oracle. This changes transport only: the oracle still checks the complete DKIM
signature, headers, body hash, timestamp and extraction template.

The real fixture needs one 24KB stored prefix and a 78,197-byte inline tail. The final helper
calldata is 80,228 bytes, below the 95KB admission bound. No synthetic future newsletter is
ever submitted to a production oracle. Browser tests use an explicitly test-only key and
synthetic fixture on a local chain.

## Verification and operational status

See [V4-ROLLOUT.md](V4-ROLLOUT.md) for official deployment sources, chain observations and
funding evidence. Run contract tests with `forge test`; opt into the real Arbitrum fork with
the environment variable documented by `test/v4/RentV4Fork.t.sol`. The v4 browser suite runs
against a local real PoolManager and explicitly labeled signed test observations.

This code has automated tests and focused adversarial review. It has not received an external
security audit. Production manifests, receipts and live checks must be recorded separately
from local and fork proof before claiming a live v4 launch.
